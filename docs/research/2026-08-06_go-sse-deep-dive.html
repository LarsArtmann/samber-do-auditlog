00Summary

The samber-do-auditlog project depends on go-sse but uses it as a bare wire-format serializer. Only three symbols are imported: sse.ContentType, sse.Event, and sse.WriteEvent. Every other capability the library offers — connection lifecycle (Stream), generic fan-out (Broadcaster[T]), heartbeat management, reconnection replay, graceful shutdown, and structured health — is hand-rolled from scratch. The hand-rolled Hub in live/hub.go (137 lines) is a near-exact functional duplicate of sse.Broadcaster[json.RawMessage].

The bottom line The project pulls in a comprehensive SSE library to use 3 of ~40 exported symbols. Adopting Stream + Broadcaster would eliminate ~200 lines of hand-rolled infrastructure (hub.go + manual SSE plumbing in server.go), gain reconnection replay for free, and unlock graceful shutdown and structured health monitoring. The library is used correctly for what it touches — it just touches almost nothing.

01Stream (Connection Lifecycle)

Missed Opportunity · High impact

Stream lifecycle entirely unused — manual flusher/headers/write management instead

live/server.go:375-425 (handleSSE) · 3 call sites bypass Stream

go-sse's Stream type manages the full SSE connection lifecycle: sets headers + writes 200 OK on construction, provides mutex-guarded Send (write + flush in one call), runs heartbeat in a separate goroutine safely, extracts Last-Event-ID for reconnection, fires OnDisconnect callbacks, and satisfies io.Closer. The consumer uses none of this.

Instead, handleSSE manually: (1) checks w.(http.Flusher) at line 376, (2) sets 4 headers individually at lines 383-386, (3) calls flusher.Flush() after every single write (4 sites: lines 415, 422, 453, 478), (4) runs heartbeat via a manual time.NewTicker + manual w.Write([]byte(": heartbeat\n\n")) at line 418. The writes have no mutex protection — safe today because heartbeat runs in the same goroutine as the event loop (select-based), but fragile if the handler is ever restructured.

Recommendation Replace the manual plumbing with sse.NewStream(w, r) + stream.Send(evt) + go stream.Heartbeat(...). Eliminates flusher checking, manual header setting, manual flush calls, and manual heartbeat bytes.

// heartbeat ticker, manual flush
func (srv *Server) handleSSE(w, r) {
  flusher, ok := w.(http.Flusher)
  if !ok { http.Error(...); return }
  w.Header().Set("Content-Type", sse.ContentType)
  w.Header().Set("Cache-Control", ...)
  w.Header().Set("Connection", ...)
  w.Header().Set("X-Accel-Buffering", ...)
  sub := srv.hub.Subscribe()
  defer srv.hub.Unsubscribe(sub.id)
  srv.sendSnapshot(w, flusher)
  hb := time.NewTicker(...)
  defer hb.Stop()
  for {
    select {
    case <-ctx.Done(): return
    case <-sub.done: srv.sendComplete(...); return
    case evt := <-sub.ch:
      sse.WriteEvent(w, sse.Event{...})
      flusher.Flush()
    case <-hb.C:
      w.Write([]byte(": heartbeat\n\n"))
      flusher.Flush()
    }
  }
}
// ~20 lines: Stream handles
// headers, flush, heartbeat, mutex
func (srv *Server) handleSSE(w, r) {
  stream := sse.NewStream(w, r)
  defer func() { _ = stream.Close() }()

  ch := srv.broadcaster.Subscribe()
  defer srv.broadcaster.Unsubscribe(ch)

  srv.sendSnapshot(stream)
  go stream.Heartbeat(
    stream.Context(), srv.config.HeartbeatInterval)

  for {
    select {
    case <-stream.Context().Done():
      return
    case <-srv.doneCh:
      srv.sendComplete(stream)
      return
    case evt := <-ch:
      if stream.Send(evt) != nil {
        return
      }
    }
  }
}

02Broadcaster (Fan-Out)

03Reconnection Replay

Missed Opportunity · High impact

No reconnection support — events lost on reconnect

live/server.go:375 (handleSSE) · no Last-Event-ID handling, no EventStore, no Replay

When an SSE client disconnects and reconnects, the browser sends a Last-Event-ID header containing the ID of the last event it received. go-sse provides Stream.LastEventID(), EventStore interface, and Replay() / ReplayFiltered() to automatically fill the gap.

The consumer has none of this. Events are broadcast with no Event.ID set (server.go:411, 449, 476 construct sse.Event without the ID field). On reconnect, the client receives a full snapshot via sendSnapshot() — which recovers the report state but misses any individual lifecycle events that fired between disconnect and reconnect.

The auditlog plugin already stores every event internally (it has plugin.Events() and plugin.EventsCount()). Implementing EventStore would be a ~15-line adapter.

Recommendation (1) Tag events with sequential IDs using sse.NewEventID(strconv.FormatInt(seq, 10)). (2) Implement EventStore as a thin adapter over plugin.Events(). (3) Call sse.Replay(stream, store, stream.LastEventID()) before subscribing to live events. 
// EventStore adapter — ~15 lines
type eventStore struct {
    plugin *auditlog.Plugin
}

func (s *eventStore) EventsAfter(lastID sse.EventID) ([]sse.Event, error) {
    all := s.plugin.Events()
    lastSeq, _ := strconv.ParseInt(lastID.Get(), 10, 64)

    var result []sse.Event
    for _, evt := range all {
        if evt.Sequence > lastSeq {
            data, _ := json.Marshal(evt)
            result = append(result, sse.Event{
                Event: "event",
                Data:  string(data),
                ID:    sse.NewEventID(strconv.FormatInt(evt.Sequence, 10)),
            })
        }
    }
    return result, nil
}

04Heartbeat

Partially Used · Medium impact

WriteHeartbeat reimplemented as a raw byte write

live/server.go:418 · 1 call site hand-rolls heartbeat bytes

go-sse provides sse.WriteHeartbeat(w io.Writer) error which writes the comment frame ": heartbeat\n\n" (event.go:187-196). The consumer writes the exact same bytes manually at server.go:418: w.Write([]byte(": heartbeat\n\n")). This is literal duplication — the bytes are byte-for-byte identical to the heartbeatFrame constant in go-sse's event.go.

Additionally, go-sse's Stream.Heartbeat(ctx, interval) runs the heartbeat in a separate goroutine with proper mutex coordination against concurrent writes. The consumer's heartbeat runs in the event-loop goroutine via select, which works but prevents the heartbeat from firing during a long snapshot computation (e.g., sendSnapshot at line 391 calls plugin.Report() which builds the full report — if that takes > 15s, the heartbeat is delayed).

Recommendation Use sse.WriteHeartbeat(w) instead of w.Write([]byte(": heartbeat\n\n")). Or better: adopt Stream and use go stream.Heartbeat(...) for goroutine-safe, concurrent heartbeat.

05Graceful Shutdown

Partially Used · Medium impact

No broadcaster drain on server shutdown — in-flight events may be lost

live/server.go:223-237 (Server.Shutdown) · only shuts down http.Server, not hub buffers

The consumer's Server.Shutdown(ctx) calls http.Server.Shutdown(ctx) which waits for active HTTP connections to finish. But the hub's subscriber buffers (channel with 128 capacity) may still contain undelivered events. When the HTTP server returns, those events are silently lost.

go-sse's Broadcaster.Shutdown(ctx) stops accepting new subscribers, waits for every subscriber's buffer to drain (consumers catch up), then closes channels. This is exactly the behavior needed for a clean dashboard shutdown — connected clients receive all queued events before the connection closes.

Recommendation If Hub is replaced with Broadcaster, chain broadcaster.Shutdown(ctx) after http.Server.Shutdown(ctx) in the server's Shutdown method.

06Health Monitoring

Partially Used · Low impact

Manual health response misses broadcaster lifecycle state

live/server.go:349-373 (handleHealth) · constructs healthResponse manually

The /api/health endpoint manually constructs a healthResponse with Clients, Events, Complete, Dropped. It queries hub.ClientCount() directly.

go-sse's Broadcaster.Health() returns a structured BroadcasterHealth with Closed, Draining, SubscriberCount, and BufferSize. Enriching the health response with Draining and BufferSize would give operators better visibility into the SSE subsystem state during shutdowns.

Recommendation After adopting Broadcaster, enrich healthResponse with broadcaster.Health() fields. Low effort, improves observability.

07Convenience Methods

Partially Used · Low impact

SendJSON / SendData convenience methods unused — manual marshal + WriteEvent instead

live/server.go:427-456 (sendSnapshot), 458-479 (sendComplete) · 2 functions manually marshal + WriteEvent

sendSnapshot and sendComplete both follow the same pattern: (1) build a struct, (2) json.Marshal(data), (3) sse.WriteEvent(w, sse.Event{...Data: string(payload)}), (4) flusher.Flush(). This is exactly what Stream.SendJSON(eventName, v) does in one call — marshal + send + flush, with error wrapping.

Similarly, the event broadcast at line 411 (sse.WriteEvent(w, sse.Event{Event: "event", Data: string(evt)})) could use Stream.SendData("event", string(evt)).

Recommendation After adopting Stream, replace sendSnapshot/sendComplete internals with stream.SendJSON("snapshot", data) / stream.SendJSON("complete", data). Eliminates manual marshal + WriteEvent + Flush boilerplate.

10Conclusion

go-sse is used at 7.5% of its API surface (3 of ~40 exported symbols). The three symbols it does use (ContentType, Event, WriteEvent) are used correctly and idiomatically. But the library's core value propositions — Stream (connection lifecycle), Broadcaster (fan-out), and Replay (reconnection) — are entirely unused, with hand-rolled equivalents filling every gap.

The single highest-leverage action is a coordinated adoption of Broadcaster + Stream + Replay (migration steps 1-3 above). This would eliminate ~200 lines of hand-rolled infrastructure, gain seamless SSE reconnection, and bring the adoption score from 22 to an estimated 85+ — moving from "token adoption" to "maximized" in one refactor.
